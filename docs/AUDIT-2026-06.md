# nm-openvpn3 security & correctness audit — 2026-06-02

Baseline at audit time: `cargo build --workspace --all-targets` ✅, `cargo test --workspace`
✅ (74 tests), `cargo clippy --workspace --all-targets --all-features` ✅ (zero warnings).
Version `0.6.0-alpha.5`, branch `rust/main`.

Method: independent full read of all ~9,600 LOC of workspace source, plus a fan-out
audit (18 finders × security/correctness/ffi/concurrency lenses → dedup → adversarial
verification against the actual code and the upstream openvpn3-linux source → quality
sweep). Findings below are the verified set; severities are post-verification (several
finder over-claims were downgraded after checking the real data flow).

Privilege model: **service runs as root** (configures routes/IP/DNS, accepts D-Bus from
NM); **auth-dialog + editor/properties cdylibs run as the user**. The code is genuinely
high-quality and already hardened (O_NOFOLLOW/O_EXCL, ABI version guard, catch_unwind FFI
guards, allowlisted route-injection defense, zeroized secrets, race-correct
connect/disconnect coordinator). The findings are mostly *silent data-loss on round-trip*
and *semantic mismatches with openvpn3/libnm*, not memory-safety or injection holes.

Legend: ☑ = fixed in this pass · ☐ = recommended, not yet applied.

## Confirmed bugs

### HIGH

**B1 ☑ `auth` HMAC digest silently dropped from the live-connect profile**
`nm-openvpn3-service/src/build_profile.rs` — `build_profile_string` never emits
`auth <digest>` (no `KEY_AUTH`, no emission). The importer stores it, the editor exposes
an "HMAC authentication" combo, the exporter (`from_nm_data`) re-emits it — but the live
connect path (used when no `.ovpn` profile file is pinned) drops it. A user who selects
SHA256/SHA512 gets it honoured in an exported file but silently ignored at connect:
handshake failure against a server pinned to a specific `auth`, or a weaker MAC than
configured (narrow — `--auth` only governs the data-channel HMAC for non-AEAD/CBC ciphers
and the tls-auth control channel). Not in the documented "Deferred" list → undocumented
silent drop. Fix: add `KEY_AUTH` and emit `auth` unconditionally alongside cipher/tls-cipher.

**B2 ☑ Open-vocabulary combos silently wipe out-of-list values on Apply**
`nm-openvpn3-editor/src/editor.rs` — `compress`, `cipher`, `auth`, `data-ciphers-fallback`
are backed by curated, *incomplete* `AdwComboRow` vocabularies but are in `WIDGET_DATA_KEYS`.
`combo_row` clamps an unlisted stored value to index 0 (`""`), the additive-replay loop
skips them (in-vocabulary), and `update_connection` writes `""` → `remove_data_item`.
Open an existing connection with e.g. `compress=stub`/`cipher=CAMELLIA-256-CBC`/`auth=SHA3-256`/
`data-ciphers-fallback=ARIA-256-GCM` and click Apply without touching the section → the
directive is silently deleted, and the UI misrepresents the value as "Default". Violates
the file's own round-trip contract. Fix: in `combo_row`, when the stored value matches no
listed choice, append it as an extra (passthrough-labelled) entry and select it — so it
round-trips and the user can still clear it by picking "Default".

### MEDIUM

**B3 ☑ auth-dialog masks the wrong NMSettingSecretFlags bit (NOT_SAVED vs NOT_REQUIRED)**
`nm-openvpn3-auth-dialog/src/main.rs:253` — `secret_required_flag` computes `(bits & 0x2) == 0`
with a comment "NOT_REQUIRED = 0x2", but per libnm (and this repo's own `libnm.rs:46-47`)
`NOT_SAVED = 0x02`, `NOT_REQUIRED = 0x04`. So a password with `flags=2` (the canonical
"don't store my password, ask every time" config) is treated as not-required → in the
no-hints inference path the dialog takes `write_no_secret` and **never prompts**, and
activation fails to authenticate with no dialog. The existing test
`flag_not_required_suppresses_password` encodes the same wrong constant and locks the bug
in. Fix: mask `& 0x4`, fix comment, fix the test, add a `flags=2 ⇒ prompt` regression test.

**B4 ☑ `CONN_DONE` mapped to Started, but it's a terminal tunnel-DOWN event**
`nm-openvpn3-service/src/status.rs:120` — `ConnectionMinor::Done` (minor 16) is grouped
with `Connected → Started`. Verified against openvpn3-linux v27 (`core-client.hpp`,
`service-client.cpp`, `sessionmgr-session.cpp`): every `CONN_DONE` emission site stops the
mainloop (inactivity timeout, emergency shutdown, post-disconnect) and the session manager
groups it with `CONN_FAILED → close_session()`. For a *backend-initiated* termination
(`disconnect_requested == false`), NM keeps showing the VPN connected for ~30s until the
poller's post-Started error budget trips, then reports a spurious `ConnectFailed`. User
disconnect is unaffected (separate path). Fix: move `Done` into the `Stopped` arm.

**B5 ☑ `has_default_route` misses the def1 full-tunnel split (0.0.0.0/1 + 128.0.0.0/1)**
`nm-openvpn3-service/src/routes.rs:79` — returns true only for a literal `0.0.0.0/0`.
Verified against openvpn3-linux netcfg (`core-tunbuilder.cpp`): redirect-gateway installs
the *def1* pair (`0.0.0.0/1` + `128.0.0.0/1`), never a literal `/0`. So for the dominant
full-tunnel case `has_default_route` returns false and the service emits
`never-default=TRUE`, telling NM the VPN is not the primary connection → VPN DNS not given
system-wide priority (DNS can leak to the ISP resolver while traffic is correctly
tunnelled). Traffic itself is not leaked (netcfg installed the routes; `preserve-routes=true`).
Fix: treat literal `/0` OR both def1 halves as a default route.

**B6 ☑ `as_nm_data` drops `keysize` on import**
`nm-openvpn3-properties/src/import_export.rs` — the import projection has no `keysize` arm,
yet `keysize` is editor-surfaced (`WIDGET_DATA_KEYS`, SpinRow, write-back) and the exporter
maps it. Importing `keysize 256` → value never reaches vpn.data → editor shows 0 and, on
Save, persists the absence; the structured build/export fallback then omits it (the common
pinned-profile path masks activation impact, bounding this to medium). Fix: add a `keysize`
import arm mirroring `auth`.

**B7 ☑ IPv6-literal `remote` corrupted by the vpn.data ⇄ .ovpn encode/decode**
`nm-openvpn3-properties/src/import_export.rs` — `as_nm_data` joins `host:port:proto` with
bare colons and never brackets an IPv6 host; `from_nm_data` splits with `splitn(3, ':')`
and no bracket handling. A bracketed `[2001:db8::1]:1194:tcp` (the form the *tested*
service-side `parse_remote` mandates) decodes to garbage `host=[2001 port=db8 …`, and a bare
IPv6 host encodes ambiguously. Corrupts the editor display and the structured export.
Fix both arms: bracket an IPv6 host on encode; strip `[...]` before colon-splitting on decode.

### LOW

**B8 ☑ `verify-x509-name` value containing a colon mis-split when no type was set**
`import_export.rs:520` and the same root cause in `build_profile.rs:334` —
`from_nm_data`/`build_profile` unconditionally `split_once(':')` and treat the prefix as the
x509 name-type. A no-type DN with a colon (e.g. `CN=Foo:Bar`) is corrupted into name=`Bar`,
type=`CN=Foo`. Fails closed (openvpn rejects the bogus type) rather than weakening
verification. Fix: only treat the prefix as a type when it equals `subject|name|name-prefix`.

**B9 ☑ HTTP-proxy auth-file password not zeroized on import**
`nm-openvpn3-properties/src/bridge.rs:198-211` — `contents`, `pass`, and the `CString` v are
dropped without scrubbing, unlike the editor write-back path which explicitly zeroizes.
Defense-in-depth gap (the password is also on disk and in the keyring). Fix: add `zeroize`
to the properties crate and `Zeroizing`-wrap the plaintext copies.

**B10 ☑ `new_secrets` lacks the teardown re-check `handle_attention` has**
`nm-openvpn3-service/src/plugin.rs:1234` — a Disconnect racing `new_secrets` (they don't
share the connect lock) makes `session_provide_input` fail against the torn-down session,
returning a spurious "could not provide N authentication slot(s)" error for a deliberate
disconnect. Cosmetic (state stays consistent). Fix: in the `Err` arm, bail `Ok(())` when
`self.coord.teardown_requested()` (NOT the tautological `session_path == path` re-check the
finder first proposed).

**B11 ☑ `--persist` flag parsed but never honoured** *(found independently; the workflow missed it)*
`nm-openvpn3-service/src/main.rs:29` + `plugin.rs:1217` — `args.persist` is parsed and logged
but never passed to `Plugin`, and `disconnect()` unconditionally `quit_tx.send(())`, so
`main`'s `select!` always exits on Disconnect. `--persist` is a silent no-op, and the
`clear_teardown`/`persist_reconnect_clears_stale_teardown` machinery (predicated on the
process surviving a Disconnect) is unreachable in production; the extensive `--persist`
comments mislead. Fix: thread `persist` into `Plugin` and gate the quit on `!persist`.

## Correctly refuted (no change)

- `ovpn3-client/src/lib.rs:385` — "Check/Fetch error silently drops a credential slot":
  real asymmetry, but self-heals across repeated AttentionRequired firings and the proposed
  fail-fast fix is net-negative (any transient bus hiccup would abort the whole connection).
- `bridge.rs:323` — "inline-blob write failure swallowed but path still added": the pinned
  `.ovpn` profile path masks it at activation; openvpn3 surfaces a clean file-open error in
  the fallback. Robustness polish, not a defect.
